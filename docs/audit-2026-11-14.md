## 1. Verdict

No high-severity defect found, and nothing I read suggests a wrong result on a path the tests and the owners' runs
cover. The 2026-11-14 changes check out on the invariants they rely on (§3): the fused norm/rotation kernel writes the
same values as `rmsnorm_quant` + `h8r_act`, its local memory and block counts are within the limits `ops.cl` needs, the
packed weight layout that `h8r_weights` / `h8r_decode` write is the one `gemm_xw8` reads, and the new OpenCL platform
choice can only pick the same device as before on a one-Intel-GPU machine.

What I did find is 7 smaller items: **one hardening gap in the runtime's `clEnqueueMapBuffer`** (the only member of the
`clEnqueue*Buffer` family that neither bounds-checks nor null-checks, L1), **one behavioural deviation of unmap** for
read-only maps (L2), a nit on `logit_bias` keys (L3), **two latent hazards whose trigger is a future edit, not today's
code** (I2, I3 — both are "one call site away", and worth a comment where the code is so that the next person cannot
widen them by accident), and **two test-coverage gaps** (the packer kernels are outside the start-up check, I1;
`src/pbkdf2.h` has no test in `tests/`, I4).

Counts: 0 high, 0 medium, 3 low, 4 info. The previous audits (`docs/audit-2026-11-13.md`, `-13b.md`) found more, and
their fixes are in place where I re-checked them (§4).

## 2. Findings

### L1. `clEnqueueMapBuffer` is the one buffer call with no bounds check and no null check

**File:** `zero/clrt.h:674-720`. **Severity:** low. **Confidence:** high.

`clEnqueueReadBuffer`, `clEnqueueWriteBuffer` and `clEnqueueFillBuffer` all start with
`if (out_of_bounds(..., b, off, n)) return -30;` (`:683`, `:693`, `:704`), and `out_of_bounds` (`:674-681`) also covers
`b == nullptr` (`b ? b->size : 0`). The map does not:

```cpp
inline void* clEnqueueMapBuffer(cl_command_queue, cl_mem b, cl_bool, cl_map_flags flags, size_t off, size_t n, ...) {
  if (ev) *ev = nullptr;
  void* h = zrt::host_alloc(n);
  if (flags & CL_MAP_READ) {
    ZE_CHECK(zeCommandListAppendMemoryCopy(zrt::imm(), h, b->ptr + off, n, nullptr, 0, nullptr));   // b, off, n unchecked
    zrt::sync();
  }
  zrt::maps().push_back({b, off, n, h});
  ...
```

**Why it matters:** with `CL_MAP_READ`, a map that runs past a buffer's end copies device memory past the allocation
(the class of fault `out_of_bounds` was written to refuse), and a `nullptr` `cl_mem` is a host-side null dereference
instead of a refused call. With `CL_MAP_WRITE` the range is only recorded, and the unmap (`:725`) then copies `n` bytes
back from offset `off` — past the end again.

**Not triggered today:** the only caller in the tree is `zero/engine_load.h:107`, which maps `0 .. total` of a buffer of
exactly `total` bytes. So this is hardening, not a live bug.

**Fix:** the same guard the three siblings use, at the top:
`if (out_of_bounds("map", b, off, n)) { if (err) *err = -30; return nullptr; }`. (Callers check `*err` with `CL_CHECK`,
so returning the error through `err` is the shape they expect.)

### L2. Unmap writes the host buffer back for a read-only map, and forgets the map's flags

**File:** `zero/clrt.h:709-732`. **Severity:** low. **Confidence:** high.

`Mapping` records `{m, off, n, host}` only (`:116`); the `cl_map_flags` are dropped. `clEnqueueUnmapMemObject` copies
the host buffer to the device for **every** mapping:

```cpp
ZE_CHECK(zeCommandListAppendMemoryCopy(zrt::imm(), b->ptr + zrt::maps()[i].off, p, zrt::maps()[i].n, ...));
```

**Why it matters:** OpenCL's `clEnqueueUnmapMemObject` writes back only a `CL_MAP_WRITE` / `CL_MAP_WRITE_INVALIDATE_REGION`
mapping; a `CL_MAP_READ` mapping is not written back (the data was never the host's to change). Today's callers map
`CL_MAP_WRITE` or map and unmap without touching a read mapping, so the values written back are the ones read — no
difference in results. But a future read-only caller that (legitimately) leaves garbage in the host copy would silently
rewrite device memory.

**Fix:** keep the flags in `Mapping` and skip the copy-back when `(flags & (CL_MAP_WRITE | CL_MAP_WRITE_INVALIDATE_REGION)) == 0`;
free the host buffer either way.

**Also in the same function:** if `p`/`b` do not match a live mapping, the call returns `-30` and the host buffer of the
map is never freed (a leak on an error path). Not reachable today (there is one map, always matched).

### L3. `logit_bias` keys are truncated `long` → `int` before the range check

**File:** `tools/server_chat.h:119-123`. **Severity:** low (nit). **Confidence:** high.

```cpp
const long t = strtol(k.c_str(), &end, 10);
if (end && *end == 0) sp.logit_bias.push_back({(int)t, (float)v.as_number()});
```

`tools/sampler.h:167,187` checks `t >= 0 && t < V` before touching the logits, so there is no out-of-bounds access —
the value is merely *wrong*: `"4294967297"` becomes token `1`, and a client that means to ban one token biases another.
OpenAI's schema takes integer token ids, so a client sending 2^32 has a bug of its own; still, the honest behaviours are
"ignore the entry" or "400", not "bias a different token".

**Fix:** `if (t < 0 || t > INT_MAX) continue;` before the push (or `std::from_chars` into an `int`, which the server
already does elsewhere).

### I1. The start-up check tests the GEMM's packed *reader*, never the packed *writers*

**Files:** `zero/xe2/engine_xw.h:210-293` (`xw_check`), `zero/kernels/h8.cl:250-267` (`h8r_weights`),
`zero/kernels/h8.cl:330-337` (`h8r_act`), `zero/kernels/decode.cl` (`h8r_decode -DXW_PACKW_OUT`).
**Severity:** info. **Confidence:** high.

`xw_check` builds the two packed layouts on the host with plain loops:

```cpp
wp[gc * 256 + ((j / 8) * 2 + cl / 8) * 64 + (j % 8) * 8 + cl % 8] = wq[gc * 256 + j * 16 + cl];     // weights
ap[((m / 8) * nch + c) * 128 + h * 64 + (m % 8) * 8 + l] = aw[m * (K / 4) + c * 16 + h * 8 + l];     // activations
```

and then runs `gemm_xw8 -DXW_PACKA/-DXW_PACKW` on them. So the check proves "the reader agrees with this layout"; it does
**not** run `h8r_act -DXW_PACKA_OUT` / `h8r_weights -DXW_PACKW_OUT` / `h8r_decode -DXW_PACKW_OUT`, which are what writes
those layouts in the engine. A drift between a packer and the reader would therefore pass the start-up check (and its
"results checked bit for bit" line, `engine_xw.h:195`) and show up as wrong logits only.

**I checked the two by hand, and they agree today.** For a token, the packed word of chunk `ch`, lane `l`, row `m` is at
`((m / 8) * (K / 64) + ch) * 128 + (l / 8) * 64 + (m % 8) * 8 + (l % 8)` (`h8.cl:334`), which is exactly the host loop's
index with `c = ch`, `h = l / 8`, `l = l % 8`. For a weight, `h8r_weights` writes
`gc * 256 + ((j / 8) * 2 + cl / 8) * 64 + (j % 8) * 8 + cl % 8` with `gc = (g * nsb + s) * 4 + ws / 16`
(`h8.cl:258-266`), the same expression with the same `gc`. The CHANGELOG's own check (27B logits identical with packing
3 / 1 / 2 and 0) is the end-to-end evidence.

**Suggestion:** have `xw_check` make its packed inputs by *running* the packer kernels on the plain data (once per
process, a few microseconds) instead of on the host — then the check covers the pair, which is what the header comment
(`engine_xw.h:27-28`) reads as promising.

### I2. The fused norm's limits live in `engine_h8.h`, the kernel that needs them in `ops.cl`: one edit away from silent corruption

**Files:** `zero/kernels/ops.cl:190-195` and `:228-253`, `zero/engine_h8.h:88-92` and `:217-232`.
**Severity:** info (latent). **Confidence:** high.

`rmsnorm_h8r` needs three things that the kernel itself cannot enforce:

1. **`K / HB <= 256 / SG`.** Each rotation block is one sub-group (`const int nblk = K / HB, bk = get_sub_group_id();`,
   `ops.cl:228`). The launch is `gws {256, Mp}, lws {256, 1}` (`engine_h8.h:231`), so a work-group has `256 / SG = 16`
   sub-groups (`#define SG 16`, `ops.cl:8`). With more blocks than sub-groups, blocks `>= 16` are never rotated and
   `for (int i = 0; i < nblk; ++i) amax = fmax(amax, red[i]);` reads `red[]` past its 16 entries (`ops.cl:195`,
   `:243-245`).
2. **`__local float rowv[H8N_K]`** fits: `(size_t)K * 4 + 64 <= 60 * 1024` (`engine_h8.h:220`).
3. **`K / HB` blocks, `red[16]`**: the same bound as 1.

All three are checked at the call site — `K / hb > 16` (`engine_h8.h:220`), and `h8_block(w.K) <= 32` in `h8_ok`
(`:91`) — and the two limits are *different* (32 comes from `h8r_act`'s `red[32]`, `h8.cl:288`, whose work-group holds
`K / HB` sub-groups by construction). Today only `engine_qwen.h` calls `rmsnorm_h8` (4 sites, all Qwen dense, `K / hb`
of 5-8), so nothing is wrong. Adding the same fusion to a model with a 7680- or 17408-wide `K` (`K / hb` of 30 / 17)
would compile, launch, and quietly produce wrong results for every block past 16 — no check, no log line.

**Suggestion:** a comment in `ops.cl` next to `red[16]` naming the requirement in the kernel's terms ("`K / HB` blocks,
one sub-group each; the caller launches 256 work-items and checks `K / HB <= 16`"), and — cheaply — a `#if` guard in
`ops.cl` (`#if HN_NV * 16 != HB #error`, and an explicit `-DH8N_NB=` from the engine that the kernel compares against
`get_num_sub_groups()`), so a mismatch fails the build or the launch instead of the result.

### I3. `h8_pre_live_` makes `h8_act` skip a rotation on a *shape* match only; today one scope = one input, but nothing enforces it

**Files:** `zero/engine_h8.h:204-243`, `zero/engine_qwen.h:21-24`, `:227-230`, `:306-309`, `:398-401`.
**Severity:** info (latent). **Confidence:** high.

`rmsnorm_h8` records `h8_pre_M_`, `h8_pre_K_` and sets `h8_pre_live_`; `h8_act` then returns without rotating when

```cpp
if (h8_pre_live_ && !h8_fsrc_ && h8_row() && Mp == h8_pre_M_ && K == h8_pre_K_) return;      // engine_h8.h:238
```

The guard knows the *shape* of the input, not *which* input it is — unlike the reuse cache next to it, which also
compares the source buffer (`h8_last_aq_ == src`, `:242`). It is correct today because every `H8Share` scope that uses
the fused norm contains exactly one norm and one input (`x_`), and the destructor clears the flag (`:176-180`). A second
norm in one scope with the same `K` and `Mp` but a different source (a shared expert's norm next to the routed one, say)
would silently read the first input's rotation.

**Suggestion:** store the source buffer (and the row offset) the way the reuse cache does, and compare them in the early
return; it costs two fields and removes the class.

### I4. `src/pbkdf2.h` has no test in `tests/`

**Files:** `src/pbkdf2.h` (new on 2026-11-13), `tools/server_remote.h:81-95`. **Severity:** info. **Confidence:** high.

The file is the Linux half of the remote-access password hash, and its header says it was checked against RFC 7914's
PBKDF2 vectors and against CNG. Everything else of its size in this tree has a CPU-only test
(`tests/test_sampler.cpp`, `test_json.cpp`, `test_xcache_pools.cpp`, ...), and this one guards an authentication
decision. I read it line by line and found no defect: `finish`'s padding handles the `n == 56 → 64 → 0 → 56` wrap
(`:53-65`), `Hmac` keeps the inner/outer states and copies them per block (`:85-92`), `derive` appends the block index
big-endian (`:99`) and XORs `iters - 1` further rounds (`:102-105`), and the truncation to `dk_len` is
`min(32, remaining)` (`:107`).

**Suggestion:** `tests/test_pbkdf2.cpp` with the RFC 7914 vectors and one password longer than 64 bytes (which takes the
`Sha256` pre-hash branch, `:71-77`) — CPU only, so it runs in CI like the others.
