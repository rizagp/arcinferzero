## 1. Verdict

* **Windows fidelity: no regression found.** Every Windows code path I checked produces the same Win32 call with the
  same arguments as before the branch. Details in §2.
* **The Linux halves are, on the whole, carefully written** (process groups, `SIGPIPE`, `EINTR`, `O_CLOEXEC`,
  `MSG_NOSIGNAL`, bounded output, per-session state). The main problems are in the seams: (a) one file is not in git at
  all, so the branch cannot build on Linux for anyone else; (b) two path helpers that were not ported still compare

Counts: 1 high, 5 medium, 10 low/nit. §9 lists what I verified as correct, including the PBKDF2 implementation.

## 4. Medium

### M1. `pdfr::Pdf::render` can throw, where the Windows half never does
**File:** `tools/pdf_render.h:69` — `if (r.exit_code != 0 || r.out.compare(1, 3, "PNG") != 0)`.
**What is wrong:** `std::string::compare(pos, …)` throws `std::out_of_range` when `pos > size()`. If `pdftoppm` exits 0
and writes nothing (an empty output stream; a page that produces no image; a future poppler that writes to a file
instead of stdout), `r.out` is empty, `pos == 1 > size()` and the call throws. The Windows counterpart
(`:133-165`) wraps the whole body in `try/catch (hresult_error) / catch (std::exception)`, so `render` is documented and
relied on as non-throwing (`const std::string png = doc.render(p, 150, err);` at `server_ocr.h:161` and `:733`, no
`try`).
**Trigger:** an OCR request for a PDF page whose render comes back empty with exit status 0.
**Effect:** the exception leaves `ocr_pdf` / `ocr_batch`; `HttpServer::run_handler` (`src/http.h:655-663`) turns it into
a 500 (`"basic_string::compare: __pos > this->size()"`), or, if the answer is already streaming, an error event that
ends the stream — instead of the intended `"[the page could not be rendered: …]"` note that lets the batch go on.
**Fix:** check `r.out.size() >= 4` before the `compare`, and/or wrap the Linux body in `try/catch` like the Windows one.
**Severity:** Medium (one broken page loses the rest of an OCR batch; no crash).
**Confidence:** High (both the throw condition and the absence of a caller `try` were read).

### M2. `plat::run_program`'s deadline does not cover the final `waitpid`
**File:** `src/platform_proc.h:103-149` — the deadline is tested only at the top of the read loop
(`while (pout[0] >= 0 || perr[0] >= 0)`, `:103-109`), and the loop is left by `break` at `:143` (both pipes closed) or at
`:115` (`if (k < 0 && errno != EINTR) break;`); `:147` then waits with `waitpid(pid, &st, 0)` — no `WNOHANG`, no retry limit.
**What is wrong:** if the child closes **both** stdout and stderr and keeps running, the loop ends as "done" without
the time limit ever being evaluated, the child is not killed (`kill_it` false), and the call blocks in `waitpid` for
ever. The same happens on a `poll()` failure (`:115`, e.g. `EINVAL`/`ENOMEM`): the pipes are closed by `close_all()`
and the caller waits indefinitely for a program it never killed.
**Trigger:** any program in the list — or a wrapper script standing in for one — that closes `1` and `2` and then
hangs; `poll` returning an error under memory pressure. In both cases the request thread (audio decode, image decode,
PDF render) is stuck holding a client connection, and for the image/audio path there is no outer timeout.
**Fix:** after the loop, reap with `waitpid(pid, &st, WNOHANG)` in the same 100 ms cadence against the deadline, and
`kill(-pid, SIGKILL)` when the deadline passes.
**Severity:** Medium (a permanent stuck request thread; a leak, not a crash).
**Confidence:** High for the code fact; Low for how easily a real tool triggers it.

### M3. `SIGPIPE` is only ignored lazily, so the server can die from its own log output
**Files:** `src/platform_proc.h:29-32` (`ignore_sigpipe`, called only from `run_program` `:54`, `server_terminal.h:97`,
`server_mcp.h:338`); no call at startup (`tools/server.cpp:949` area installs only the crash handler; grep shows no other
`SIGPIPE` handling).
**What is wrong:** on Windows a closed log pipe yields a write error; on Linux it is `SIGPIPE` and the default action
ends the process. Until the first terminal command / MCP start / external program, `serverz` dies if its stderr (or
stdout) is a pipe whose reader is gone.
**Trigger:** a start script like `serverz … 2>&1 | head -40`, or a supervisor that closes its end; the first log line
after the reader exits kills the server (silently, exit 141).
**Fix:** call `plat::ignore_sigpipe()` at the top of `main`, before any logging.
**Severity:** Medium (silent death of a headless server; documented failure mode of the old code is "nothing").
**Confidence:** High.

### M4. Unported `L'\\'` path logic: project file access is broken, and one failsafe fails open
**Files:** `tools/server_projects.h:89-92` (`under`), `:143` (`resolve_in`), `:64-72` (`id_of`);
`tools/server_ocr.h:399-404` (`ocr_in_project`); both are compiled on Linux (no `_WIN32` guard).
**What is wrong:** three separate problems, all from keeping the Windows separator and case folding:

1. `resolve_in` (`:143`) requires `x[r.size()] == L'\\'`. On Linux that byte is `/`, so **every**
   `project:<id>/<rel>` file is refused with *"outside the project's folder: rel"*. `read_file`, `search_file`,
   `digest_file` and a project's OCR output path all go through it.
   **Trigger:** any project chat that asks to read a file of the project.
2. `refuse()`'s `under()` (`:92`) has the same `L'\\'` test, so *a subfolder of the data folder* — the chats, caches,
   memory — is **not** recognised as being inside it, and `refuse()` returns `""` (accepted). The same branch is the
   only protection for `$HOME`; the loop over `AppData/.ssh/.gnupg/.aws/.azure/.config` sits inside
   `if (const char* up = getenv("USERPROFILE"))`, which is unset on Linux, so on Linux **`~/.ssh` and the whole
   `$HOME` can be chosen as a project folder.** The `SystemRoot` / `ProgramFiles` / `…/Windows` checks are inert for
   the same reason.
   **Trigger:** `POST /v1/projects` with `{"folder": "$HOME/.ssh"}` or `"$HOME/.inferzero/chats"`.
3. `id_of` (`:64-72`) lowercases with `towlower` and round-trips through `wstring`. On a case-sensitive filesystem
   `/srv/Proj` and `/srv/proj` become one id; and `path::wstring()` converts through the global locale's codecvt, which
   under the default `C` locale cannot represent non-ASCII bytes, so a project folder with an accented name can throw
   or be mangled depending on `LANG`.
**Fix:** a `plat::path_under(a, b)` helper (separator, case sensitivity, `lexically_relative`), used by both files; a
`$HOME`-based brother of the `USERPROFILE` branch.
**Severity:** Medium (breaks a documented feature; weakens a security check).
**Confidence:** High for 1 and 2 (pure string logic), Medium for the exact failure mode of 3 (locale-dependent).

### M5. The crash handler is not async-signal-safe, and cannot report a stack overflow
**File:** `src/crash_log.h:88-118`.
**What is wrong:**
1. The handler calls `fprintf`, `fflush`, `strsignal`, `raise`, `backtrace` and `backtrace_symbols_fd`, and then
   `extra()` — which `server.cpp:950` sets to `zrt::print_last_launch()`, a function that builds `std::string`s
   (`watch_args(...).c_str()`, `zero/clrt.h:845-864`) and walks shared structures. None of that is async-signal-safe:
   if the fault happened while another thread held the `stderr` `FILE` lock (the logger does, on every line) or the
   allocator lock, the handler deadlocks or recurses instead of printing anything. The Windows half has the same class
   of problem, but there the filter runs on the faulting thread with a different contract, and the code here is new.
2. No `sigaltstack`: a stack-overflow `SIGSEGV` (deep recursion in the engine, which is the most likely way this
   program dies) runs the handler on the exhausted stack, faults again, and — with `SA_RESETHAND` already in
   effect — dies with no message at all.
3. `raise(sig)` re-raises with `si_code == SI_TKILL` instead of re-executing the fault, so a core file loses the
   original fault address/code (only cosmetic given the printed address, but it defeats `si_code` based triage).
**Trigger:** any segfault that happens while another thread is logging (i.e. almost always in this server).
**Fix:** only `write(2)`, a pre-warmed `backtrace` and a static buffer inside the handler; `sigaltstack` +
`SA_ONSTACK`; `extra()` restricted to pre-formatted bytes.
**Severity:** Medium (the feature that exists to make a crash diagnosable can silently do nothing).
**Confidence:** High.

### M6. The new Linux code uses GNU-only interfaces and nothing defines `_GNU_SOURCE` / `_DEFAULT_SOURCE`
**Files:** `src/platform_proc.h:61` and `tools/server_mcp.h:366` / `tools/server_terminal.h:154` (`pipe2`),
`tools/server_mcp.h:375` / `tools/server_terminal.h:160` (`posix_spawn_file_actions_addchdir_np`),
`tools/server_remote.h:73` (`getrandom` via `<sys/random.h>`), `src/platform.h:548` (`gettid`).
**What is wrong:** `pipe2`, `posix_spawn_file_actions_addchdir_np` and `gettid` are declared by glibc only under
`_GNU_SOURCE`; `getrandom` only under `_DEFAULT_SOURCE`/`_GNU_SOURCE`. In strict ISO mode (`-std=c++20`, which
defines `__STRICT_ANSI__`) neither is on, and no file, build script or doc line in the tree defines them
(`grep -rn "_GNU_SOURCE"` → nothing; there is no `CMakeLists.txt` yet).
**Trigger:** the documented build line of `docs/linux-port.md:102` (`g++ -std=c++20 …`).
**Fix:** `-D_GNU_SOURCE` (or `-std=gnu++20`) in the build line and in `docs/linux-port.md`, or `#define _GNU_SOURCE`
at the very top of the two headers that use `pipe2`.
**Severity:** Medium (build break; cheap fix).
**Confidence:** Medium — I did **not** compile (per the brief). The `gettid` precedent on the `runz` line suggests the
build may already be done with `gnu++`, in which case this is only a documentation gap.

## 5. Low and nits

### L1. `posix_spawn_file_actions_addchdir_np`'s result is ignored (terminal and MCP)
**Files:** `tools/server_terminal.h:160`, `tools/server_mcp.h:375`.
**What is wrong:** glibc performs the `chdir` in the child and, when it fails, exits the child with status 127
(`SPAWN_ERROR`) — `posix_spawn` itself returns 0. The result is a command that never ran, `exit_code 127`, empty
output, no error text, and for the terminal the session state is still rewritten.
**Trigger:** the chat folder or project folder deleted (or renamed) between the `is_directory` check
(`server_file_tools.h:953-968`) and the spawn; a `"cwd"` in `mcp.json` that does not exist.
**Fix:** check the return value and pre-check the directory (or use `fork` + `chdir`), and treat exit 127 with empty
output as "cannot start in DIR".
**Severity:** Low. **Confidence:** High for the terminal (127), Medium for the exact glibc behaviour (well documented
in `spawni.c`).

### L2. `kill(-pid, …)` after the child has been reaped is a PID-reuse race
**Files:** `tools/server_terminal.h:210` (unconditional `kill(-pid, SIGKILL)` after `waitpid` succeeded at `:198`),
`tools/server_mcp.h:537` (same shape at `:534-538`).
**What is wrong:** once `waitpid` has reaped the child the group only exists if members remain; in the window between
reap and `kill`, a new process can take that PID and become a group leader, and would then be killed. The window is
small but completely unnecessary.
**Fix:** kill the group **before** reaping, or keep a `pidfd`.
**Severity:** Low (would kill an unrelated process — a security-relevant "theoretically"). **Confidence:** High for the
code shape, Low for the probability.

### L3. The terminal's state file is written non-atomically, and its temp files leak on a kill
**Files:** `tools/server_terminal.h:240-241` (state), `:119-121` (`/tmp/inferzero-*`), `:643-660` (`audio`),
`tools/pdf_render.h:32-40` (`/tmp/inferzero-pdf-*`).
**What is wrong:** (a) the session state is written with `std::ofstream … trunc` in place; a crash mid-write leaves
invalid JSON, which `term::run` then silently treats as "no session" (cwd and exported variables lost) — the repo
already has an atomic helper (`files::Store::write`, `write_shared`); (b) `/tmp` is hard-coded everywhere, ignoring
`TMPDIR`, so on a system with a small `tmpfs` `/tmp` an hour of decoded audio (or a 200 MB PDF) fills it; (c) a
`SIGKILL`ed server leaves those files behind (only the `Gone`/`Tmp` destructors unlink).
**Severity:** Low. **Confidence:** High.

### L4. `read_shared` / `read_head` on Linux block on a FIFO, and accept any non-directory
**File:** `tools/server_files.h:48-58, 79-86` (via `plat::SeqFile::open`, `src/platform.h:370-386`, which refuses only
`S_ISDIR`).
**What is wrong:** `open(path, O_RDONLY)` on a FIFO blocks until a writer opens it, so a request thread hangs with no
timeout. `read_head` would also happily read 1 GiB from a symlink to `/dev/zero`. Windows has no reachable equivalent
(`CreateFileW` on a file path), so this is new behaviour.
**Trigger:** `mkfifo x` in a chat folder with the terminal tool, then `read_file x`.
**Fix:** `O_NONBLOCK` for the open, then check `S_ISREG`.
**Severity:** Low (self-inflicted denial of service). **Confidence:** High.

### L5. The external-tool calls: small gaps in the ffmpeg / ffprobe / poppler paths
**Files:** `src/audio.h:608-655, 738-745, 948-970`; `src/image.h:76-103`; `tools/pdf_render.h:26-75`.
* `ff_audio` (`:626`) ignores `r.timed_out` → a hung decode after 24 h is reported as `"exit 137"`; worse,
  `decode_mono_pcm16` (`:948-970`) checks nothing at all and returns a **silently truncated** transcript input.
* `duration_seconds` (`:738-745`) parses with `atof`, which is locale-dependent: under `LC_NUMERIC=de_DE`,
  `"123.456"` becomes `123` (a 0.4 % error today, an unbounded one for a long file). Use `strtod` with the `C` locale
  or parse the digits by hand.
* `ff_decode_bytes` (`:643-660`) and `pdfr::Pdf::open` (`:32-48`) break out of the write loop on **any** error,
  including `EINTR`, and then report "the temporary file could not be written". Retry `EINTR`.
* No `--` / `-i` guard: a path that starts with `-` (a file literally named `-i` in a chat folder, reachable through
  `record`/`upload`) is parsed as an option by ffmpeg/ffprobe/pdfinfo. Prefix with `./` or `-i` + `./`.
* `image.h:82` builds `std::string((const char*)bytes.data(), bytes.size())`; for an empty vector `data()` may be
  `nullptr`, which is technically not a valid argument. Guard `bytes.empty()`.
* PPM parsing (`image.h:83-102`) is correct (bounded digits, `maxval == 255`, 64 Mi-pixel cap, remaining-length check
  before the copy, `cut`/`timed_out` treated as errors) — the one nit is that the cap is enforced **after** ffmpeg has
  decoded, with only the 200 MB pipe limit in front of it.
* `pdf_render.h:57` runs `pdfinfo` **again for every page** (50 pages → 50 extra processes, each up to 60 s) and
  `:67` gives `pdftoppm` 120 s per page, so one OCR request can hold a thread for over 1.5 h in the worst case
  (`kOcrMaxPages = 50`); there is no per-request budget.
* `pdftoppm` with `-singlefile` and **no** output prefix is expected to write to stdout (the code reads PNG from the
  pipe). I could not confirm this without running poppler; it is the one argument in this area that needs a real test.
**Severity:** Low each. **Confidence:** High for the code facts; the `pdftoppm`/stdout one is flagged as unverified.

### L6. `whisper::compression_ratio` measures the same text differently on the two systems
**File:** `src/whisper.h:530-556`.
**What is wrong (not a bug, a behavioural difference to record):** Linux uses zlib's `compress2` at level 6 and counts
the 2-byte header + 4-byte Adler-32 (`zn`); Windows uses MSZIP and adds 4. The ratio therefore differs slightly between
the two, and the Whisper fallback threshold (`:1085`, `ratio > 2.4`) can trigger on one system and not the other. The
Linux figure is the closer one to OpenAI's own measure (zlib), which is what the comment claims.
**Also:** the `dlopen` handle is intentionally never closed (fine, it is process-lifetime), and the output buffer
(`n + n/1000 + 64`) is provably ≥ `compressBound(n)` — no overflow. `plat::dl_sym` → function-pointer cast is valid on
POSIX but not strictly portable C++ (warning-level only).
**Severity:** Nit. **Confidence:** High.

### L7. MCP: `send()` can block for ever while holding `write_mu_`, and `cleanup()` waits for that mutex
**File:** `tools/server_mcp.h:681-698` (`send`), `:524-551` (`cleanup`).
**What is wrong:** `cleanup()` takes `write_mu_` (`:528`) before closing `in_`; a caller thread inside `send` writing a
large request to a stdio server that has stopped reading blocks in `::write` (64 KB pipe buffer), holding that mutex.
`stop()`, `~Client()`, `stop_all()` and the next `ensure_started()` then hang — including at process exit. A message
larger than the pipe buffer is easy (a tool argument carrying base64). The Windows half has the identical shape with
`WriteFile`, so this is **not new**, but the Linux half could fix it cheaply with `poll(POLLOUT)` + a deadline.
**Severity:** Low (pre-existing pattern; a shutdown hang). **Confidence:** High.

## 6. PBKDF2 against the RFCs (and against CNG)

**File:** `src/pbkdf2.h:1-112`. I read the implementation line by line; it is textbook-correct.

* **SHA-256 (FIPS 180-4):** the 64 constants, the message schedule (`s0 = rotr 7/18 >> 3`, `s1 = rotr 17/19 >> 10`),
  the round function and the initial/final state are right; big-endian words on input and output.
* **Padding:** `finish` captures `bits = len * 8` **before** appending `0x80` (so the `len` bump inside `add` is
  harmless), then zeros until `n == 56` (the loop wraps through a block correctly: for a 56-byte message it appends
  7 + 56 = 63 zeros, giving exactly 128 bytes) and an 8-byte big-endian length. Correct for every length, no
  infinite-loop or off-by-one path.
* **HMAC (RFC 2104):** key block zero-padded to 64; keys longer than 64 hashed first (the remaining 32 bytes stay
  zero, as required); inner/outer pads pre-digested and copied per `mac()`, so `mac` is re-entrant and the
  `h.mac(u, 32, u)` in-place call in `derive` is safe (the write happens only after `u` has been consumed).
* **PBKDF2 (RFC 8018):** `U1 = PRF(P, S || INT_BE(i))`, `Uj = PRF(P, Uj-1)`, `F = U1 ^ … ^ Uc`; the block index is
  appended big-endian (`for (int i = 3; i >= 0; --i)`); truncation to `dk_len` is correct; `dk_len == 0` returns
  empty.
* **Against CNG (`server_remote.h:82-95`):** both derive 32 bytes of `PBKDF2-HMAC-SHA256(password, salt, iters)` over
  the same raw password bytes and hex-encode them lower-case, so a password set on Windows verifies on Linux and vice
  versa. A hash file written by one system is byte-identical to what the other would write.
* **Not verified here:** no test vector was executed (no build in this audit). The file's own comment claims it was
  checked against RFC 7914's vectors and CNG, but nothing in the diff is a test; `tests/` has no PBKDF2 case. Worth
  adding: RFC 6070-style vectors for SHA-256 (`P="password", S="salt", c=1, dkLen=32`) plus one cross-check against
  CNG in `tests/`.
* **Nits:** `iters == 0` silently yields `U1` (CNG rejects 0); `finish()` is not idempotent (harmless today, since
  only `Hmac::mac`'s copies are finished); missing `<algorithm>` (see H1).

## 7. `getrandom`

**File:** `tools/server_remote.h:66-80`. The loop handles `EINTR`, rejects `0` and negatives, and throws with a message
(otherwise a session token or a PBKDF2 salt would silently be short). Correct. Two notes: `<cerrno>` is not included
(it works through `platform.h`'s `#include <cerrno>`), and there is no `/dev/urandom` fallback — on a kernel without
`getrandom` (pre-3.17) or a seccomp profile that blocks it the whole remote-access feature throws, where
`BCryptGenRandom` on Windows would not. Ubuntu 24.04 is fine.

`libz` (`src/whisper.h:536`) and `libcurl` (`src/curl_min.h`, earlier on this branch) are `dlopen`ed, never closed, and
their absence is handled (`compression_ratio → 1.0f`, the web tools answer with an error). `dl_open(nullptr, "libz.so.1")`
would also want a `libz.so`/`libz.so.1.2.13` fallback on a distribution without the `.so.1` symlink; the same
`(Compress2)` cast of a `void*` is technically not guaranteed by C++ but is the POSIX-sanctioned pattern.

## 8. What I checked and found correct (no finding)

* **`plat::run_program`** — the parts that are easy to get wrong are right: all six pipe ends are closed on every exit
  path (`close_all` at `:56-60` and the failure branch at `:88-92`); `pipe2(O_CLOEXEC)` plus `posix_spawn_file_actions`
  means the child gets nothing extra and no fd leaks into it; stdin is closed as soon as the input is fully written or
  empty; `EINTR`/`EAGAIN` are retried on `read` and `write`; the pipe ends are `O_NONBLOCK` in the parent only (the
  child's ends are separate open file descriptions, so its stdin/stdout stay blocking — this is the subtle thing that
  could have gone wrong and did not); `POLLHUP`/`POLLERR`/`POLLNVAL` all end in a `read` that returns 0 or a handled
  errno; output is bounded (`max_out` for stdout with `cut`, 64 KB for stderr; the `min(cap, size)` arithmetic cannot
  underflow); the time-out kills the whole group with `SIGKILL` before reaping; leftovers in the group are killed after
  a normal exit (job-object semantics); `SIGPIPE` is restored to `SIG_DFL` and the signal mask cleared for the child;
  the `on_out` contract ("must not throw") is honoured by the single caller that uses a callback (`audio.h:615-623`
  traps the exception into an `exception_ptr` and rethrows after the child is gone) — the weakest point is the
  `waitpid` deadline (§M2).
* **Terminal tool** — the session model is sound: the command goes into a `mkstemp` file (not a `-c` string), stdin is
  `/dev/null` via `addopen`, the EXIT trap is single-quoted so `$1`/`$2` are expanded at trap time, `pwd -P` and
  `env -0` (NUL-separated, so no quoting problem) are read back and merged against a freshly computed `base` map,
  `PWD`/`OLDPWD`/`SHLVL`/`_` are excluded from the diff, removed variables are recorded as JSON `null`, the stored
  `cwd` is validated with `is_directory` before use, a corrupt or absent state file falls back to a fresh shell, the
  state is **not** written when the command was killed (matching the documented rule and the PowerShell `finally`),
  the venv `deactivate` is redefined for the next call, the output stays inside `kMaxOut` (48 KB head + 16 KB tail,
  same figures as the Windows copy), a background job that outlives the shell cannot hold the call open (the pipe is
  drained for at most 2 s and the read end is closed), and `cancelled()` is polled on the same 200 ms cadence as
  Windows. No `fork` in a threaded process, so no allocator-after-fork hazard.
* **MCP client** — no zombie and no use-after-free: `cleanup()` closes stdin first (so a well-behaved server exits by
  itself), waits 1.5 s, kills the group, reaps with `EINTR` retry, then sets `stop_` and joins **both** readers before
  closing their fds; `read_some` checks `stop_` before every 200 ms poll, so the join cannot deadlock on a grandchild
  holding the pipe (this is the Linux answer to the Windows "graveyard" and it is simpler and safer); `spawn()` resets
  `stop_`/`dead_`, clears the replies under the mutex, and closes all six pipe ends on a spawn failure; `~Client()` and
  `stop()` both go through `start_mu_` and are idempotent (`proc_ > 0`, `in_ >= 0` guards); `send()` retries `EINTR`
  and reports a closed pipe; the environment merge (base + `PYTHONIOENCODING`/`PYTHONUTF8` + the config's) mirrors the
  Windows `_wcsicmp` merge; `find_program` handles `PATH` unset, an empty `PATH` element (`"."`), and a command with a
  `/`. `request()`'s `Waiting` guard erases both `waiting_` and `replies_` on every exit path.
* **File layer** — `read_shared`/`read_head`/`write_shared`/`Store::write` on Linux: the 2 GiB refusal matches
  Windows, a partial read clears the buffer instead of returning half a file, the temp file is in the same directory so
  `rename` is atomic, a failed rename removes the temp file, and the names carry the pid and a per-process counter so
  two writers never collide. `fs::path` + `std::ofstream` handle non-ASCII names on Linux natively.
* **Image decode** — the PPM header parser is bounded and cannot over-read; `maxval != 255`, zero/oversized dimensions,
  a short payload, a cut pipe and a time-out are all refused with the same message the Windows path uses.
* **`plat::SeqFile`-based reads, `same_file`, `is_link`, `is_hidden_or_system`, `ram_total`** — the Linux halves are
  the right POSIX calls, and the Windows halves are the calls that were there.
* **`dbus`/socket expectations** — sockets were done in `src/platform_net.h` before this branch's tail; nothing in the
  diff re-introduces a bare `send`/`recv`/`close` on a socket.
* **web_view stub** — the signature matches the Windows one (including the default arguments), the message is accurate
  and actionable, and nothing calls into the missing Edge/Chromium machinery.
