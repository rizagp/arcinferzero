## 1. The MCP reader threads are still joined without a limit

**File:** `tools/server_mcp.h:381-413` (`cleanup()`), called from `stop()` (`:241`), `ensure_started()` (`:199`,
`:219`) and `stop_all()` (`:604`).

```cpp
for (int k = 0; k < 20 && reader_.joinable() && !dead_; ++k) Sleep(100);
if (out_) CancelIoEx(out_, nullptr);
if (err_) CancelIoEx(err_, nullptr);
for (std::thread* t : {&reader_, &err_reader_}) {
  if (!t->joinable()) continue;
  HANDLE h = (HANDLE)t->native_handle();
  for (int k = 0; k < 100 && WaitForSingleObject(h, 50) == WAIT_TIMEOUT; ++k) CancelSynchronousIo(h);
  t->join();                       // <- after at most 5 s of best-effort cancels
}
if (out_) CloseHandle(out_), out_ = nullptr;   // (closed only after the join)
if (err_) CloseHandle(err_), err_ = nullptr;
```

`CancelSynchronousIo` is best effort (as the comment above it says): if it does not abort the `ReadFile`, or the reader
is between two reads inside a callback when the 5 s run out, `t->join()` waits until the pipe closes. The pipe closes
when the last process holding its write end ends — and this cleanup exists precisely for the case where a process
**left the job** (a grandchild started through COM or WMI) and keeps the write end open. `cleanup()` runs on the HTTP
thread of `/v1/mcp/stop` (and on `/v1/mcp/enabled` turning a server off), so that request never answers; at the end of
the process (`stop_all`) it keeps the server from exiting.

The same round of fixes did it right in `tools/server_terminal.h:214-221`:

```cpp
if (out->done) reader.join();
else reader.detach();  // (it ends, and closes the pipe, when the process holding it does)
```

**Why it was not done the same way here:** `read_loop()` uses `this` (the `Client`'s handles, `mu_`, `on_message`), so
detaching is not safe with the object freed under it. That is not a reason to join blindly — it is a reason to close
the read handles first.

**Fix (either):** (a) duplicate `out_` / `err_` for the reader threads (`DuplicateHandle`) and close the `Client`'s
copies before the join, so the blocking `ReadFile` returns `ERROR_INVALID_HANDLE`; or (b) make the reader own its
handle (share a small state object with a `shared_ptr`, as a terminal read does), then `detach()` after the cancel
loop. Do not leave a bare `join()` after a bounded number of attempts: the project's own rule is that no wait is
unbounded.

## 2. A crafted GGUF can ask for ~10x its size in RAM before anything is validated

**File:** `src/gguf.h:306` (the count checks), `:319` (`tensors.resize`), `:292` (an array's vector), `:199-207`
(`split.count`).

```cpp
uint64_t nt = rd<uint64_t>(), nkv = rd<uint64_t>();
// (a key-value pair takes 12 bytes or more, a tensor entry 24: counts the file cannot hold are refused before
//  anything is allocated for them)
if (nkv > (size_ - pos_) / 12 || nt > (size_ - pos_) / 24) throw std::runtime_error("gguf: bad tensor / key count");
...
tensors.resize(nt);                  // GgufTensor = ~80 bytes + an entry in tensor_index + 8 in offs
```

The bounds are exact minimums for the *file* (8-byte length + 4-byte type = 12; 8 + 4 + 0 dims + 4 + 8 = 24), but the
in-memory rows are much bigger: a `GgufTensor` is a `std::string` (32) + type (4+pad) + a `std::vector` (24) + a
pointer (8) + `nbytes` (8) ≈ 80 bytes, plus a node in `tensor_index` (~48) and 8 bytes in `offs` ≈ **~140 bytes per
24 on-disk bytes**; a key/value row is a `std::string` key (32 + heap) + a `GgufValue` variant (≥40) + an
`unordered_map` node (~64) ≈ **~130 per 12**. So a 1 GB file can declare ~44 M tensors (6 GB) or ~89 M keys (11 GB)
*and the file can really contain them*. This is not memory-unsafe — `bad_alloc` comes out of the constructor and the
load fails — but it is a denial of service a loaded model file can cause, on a machine that also has a GPU share in
use. A 2-3 GB crafted file can exhaust a 32 GB laptop.

Two more in the same function:

- `std::vector<int64_t> v(n)` (`:292`) for an array of `int32` / `uint32` / `float` elements: `n` may be
  `remaining / 4`, and each element is stored in 8 bytes, so a 1 GB stream can ask for 2 GB.
- `open_parts()` (`:199-207`) takes `split.count` from the file with no upper bound; `for (int64_t k = 2; k <= n; ++k)`
  stops only when a part is missing, and the part's number is built with `snprintf(num, sizeof num, "%05d", (int)k)`
  into 8 bytes, so past 9,999,999 the digits are silently truncated, and `(int)k` overflows past `INT_MAX`
  (undefined). The parts it opens are inside the model's own folder, so this is not a path escape — only a wrong
  filename and an unbounded loop count.

**Fix:** cap the counts to values no real model reaches (`nkv`, `nt` ≤ 1,000,000; `split.count` ≤ 1,024), and refuse
anything above with the file's name, before `resize`. For arrays, store the element type's own width or cap `n` (e.g.
64 M elements), so a 4-byte stream cannot become an 8-byte vector. If a future model needs more, the cap can be raised
with an error message that says so; no real GGUF is close.

## 3. PDF numbers are cast without a range check

**File:** `tools/doc_reader.h:348` (`atof`), `:359`, `:507`, `:643-646`.

```cpp
o->n = atof(w.c_str());          // "1e999" -> inf, and "999999999999999999999" -> 1e21
...
o->ref = (int)o->n;              // :359  a ref number, cast with no check
...
if (target->t == Obj::Num) return (int)target->n + 1;          // :507  a page index
...
for (int k = 0; k < (int)np->n; ++k) {                          // :643  an object stream's count
  ...
  idx.push_back({(int)a->n, (size_t)b->n});                     // :646  object number and offset
```

A `double` to `int` / `size_t` conversion outside the destination's range is undefined behaviour in C++ (MSVC emits
`cvttsd2si`, which yields `0x80000000`, but the language does not promise that). The same file already knows this and
guards it in two places:

- `:617`, `P len = o->get("Length");  // (checked as a double first: a cast of -1 or 1e300 to size_t is UB)`;
- `tools/pdf_images.h:97`, `(int)std::clamp(v->n, -1e9, 1e9)` with `std::isfinite`.

**Impact:** a damaged or hostile PDF (they come from the internet through `web_fetch` and the file tools) can make the
outline point at a nonsense page, an object stream's offsets nonsense, or a reference number negative — all of which
are then range-checked or fail to resolve, so the likely visible result is a wrong outline entry or a page that reads
as empty, not memory corruption. It is still UB in a parser of untrusted input, and the fix is three lines.

**Fix:** one helper like `pdf_images::num()` (`isfinite` then `std::clamp`) for object numbers and counts, and
`std::clamp(v->n, 0.0, (double)body.size())` for an offset; use it at `:359`, `:507`, `:643` and `:646`.

## 4. The `--ctx auto` cache is read with `std::stoi` and trusted

**File:** `tools/server_catalog.h:588-609` (`cached_ctx`), `:638-646` (hit path), `:721-727` (append).

```cpp
if (cached_ctx(key, r)) return r;          // :641 — a hit is returned as written, without floor_of()
...
r.ctx = std::stoi(c[0]);                   // :602 — throws on anything not a number
```

`zero\ctx-auto.txt` is appended to (`:723`) and never pruned or rewritten, and it is read back at every
`--ctx auto` load. Two consequences:

1. **A damaged row fails the load.** A truncated line from a crash during the append, or two servers appending at
   once, can leave a line whose first field is not a number; `std::stoi` throws `std::invalid_argument`, and
   `auto_ctx` lets it out, so `load_model` fails with `"invalid stoi argument"` — a message that does not name the
   file, and no request path recovers (the user must delete `ctx-auto.txt`). Old rows without the memory parts are
   handled (`c.size() < 2`), the numeric field is not.
2. **A cached value has no floor.** A row truncated inside the context digits (`12345` → `12`) is returned as
   `ctx = 12`; the load then serves a 12-token context (or fails on a prompt longer than 12 tokens) instead of the
   4,096-token floor the fresh computation applies (`floor_of`, `:699`). The hit path does not re-check `>= 0` either;
   only `load_model` refuses `ctx <= 0`.

The file's other reads are careful by comparison: `tools/server_cache.h:376-390` checks every field of a saved
conversation (`h[2]` 0..2^24, `g[2]` 0..16, positions against the context) before resizing or using it.

**Fix:** parse with `from_chars` / `try` + `catch`, skip a row that does not parse (as the `c.size() < 2` check
already does), and apply `floor_of()` (or at least a `std::max(r.ctx, 4096)`) to a hit. Prune the file (keep the
newest N rows, or rewrite it at start) so it cannot grow with every settings change.

## 5. A chat folder's reserved names are case-sensitive on Windows

**File:** `tools/server_files.h:714` (`scan()`), `:626` (`free_name`), `:430` (`chat_put`).

```cpp
// scan(): skips the chat's own files
if (!f.is_regular_file() || fn.rfind(".", 0) == 0 || fn == "chat.json" || fn == "chat.json.tmp") continue;
...
// free_name(): case-insensitive, so files the server creates cannot take them
const std::string low = lower(name);
if (low == "chat.json" || low == "chat.json.tmp" || fs::exists(dir / name, ec)) { ... }
```

The creation path is right (BUGS.md 3), the reading path is not: Windows resolves `chat.json` and `CHAT.JSON` to one
file. A file named `CHAT.JSON` in a chat's folder — made by the in-chat terminal (`run_command`), by a user in
Explorer, or by an old version — is therefore

- listed by `scan()` as a normal user file (it is not skipped, and its own name is kept), so it shows in the Files
  panel and can be downloaded or deleted;
- *read as the chat* by `chat_get()` (`dir / "chat.json"`), so opening that chat shows the user's file instead of a
  conversation;
- **overwritten** by the next `chat_put()` (`fs::rename(tmp, dir / "chat.json")` replaces the same directory entry),
  or the save fails with "cannot write" if the user still has it open.

`free_name`'s lower-casing keeps this from happening for uploads and `create_file`; only `chat_put`'s own reserved
name is affected. Severity is low (the file has to be made outside the API), but "reserved" should mean reserved at
every comparison, not only at creation.

**Fix:** compare with `lower(fn)` in `scan()` (`:714`) and keep the exact name for display, and treat any case variant
of `chat.json` / `chat.json.tmp` as the chat's own file there; `chat_put` keeps the same rule.

## 6. Control bytes from a model file reach `/metrics` and the log

**Files:** `tools/server_metrics.h:130-138` (`esc`), `src/log.h:60-95` (`emit`), `tools/server_load.h:196-201`,
`src/gguf.h:261-265` (`rd_str`).

```cpp
// server_metrics.h
inline std::string esc(const std::string& s) {   // label value
  for (char ch : s) {
    if (ch == '\\' || ch == '"') o += '\\';
    if (ch == '\n') { o += "\\n"; continue; }
    o += ch;                                     // \r, \0 and 0x7f pass through
  }
}
```

`r.arch` and `r.model` come from outside: the architecture is the GGUF's `general.architecture`, which `rd_str()`
returns as an arbitrary length-prefixed byte string, and `--alias` is free text. `esc` is the only filter in
`/metrics`; a CR there is not a Prometheus escape, so the line ends early (or the parser rejects the value), and a
NUL is passed through as a raw byte. `emit` (`src/log.h`) does the same for the log: `%.*s` prints every byte but a
NUL, and only a line's *trailing* CR is trimmed when a line is split. The `model:` line
(`tools/server_load.h:197`) prints `h.arch` this way; error messages print tensor names the same way.

The other places that take text from outside already flatten it, which is the point of the finding — this is an
inconsistent spot, not a design decision:

- `tools/server.cpp:1481-1482` maps a request path's control bytes to `?` before the access line;
- `tools/server_startup.h:69-70` does the same for `ARC_*` values.

**Impact (low):** a model file with a CR in its architecture name rewrites the line it is printed on — in Windows
Terminal and in `server.log`, which is exactly what users paste into issues — and a CR/NUL in a label value makes the
`/metrics` text invalid for the scraper. No memory safety, no injection into another file. A model downloaded from a
hub is untrusted text, though, and the project's rule since 11-12b #2 has been that text it did not write itself is
flattened.

**Fix:** in `esc`, map `\r` to `\\r`, and any other byte `< 0x20` or `0x7f` to `?` (Prometheus has no escape for them);
in `emit`, replace control bytes except `\t` in the finished line, or flatten `arch` / tensor names / aliases where
they enter the log. Flattening in `emit` would not change runz's output today (no control bytes in its lines).

## 8. The pending-line buffer's destructor ignores the verbosity

**File:** `src/log.h:113-123` (`Pending`), `:124-160` (`vlog`).

```cpp
struct Pending {
  std::string s;
  ~Pending() {
    if (!s.empty() && cfg().on) emit(guess(s.data(), s.size()), s.data(), s.size());   // no level filter
  }
};
```

`vlog` appends to that buffer *before* `emit` decides whether the line passes the level, so a `LOG_DBG` (or a
`--log-verbosity 0` message) printed **without its `\n`** stays in the buffer; when the thread ends, the destructor
emits it at whatever level `guess()` reads from its text (W / E / I), i.e. it is printed at `-lv 0`. The same buffer
also makes `zlog::raw` (which writes directly, no buffer) able to land inside a held partial line.

Today every `LOG_DBG` and every server message ends with `\n`, and the old `\r` progress bars are guarded by
`loadp::st().on` (`zero/expert_store.h:503-507`) or are CLI-only (`zero/transcribez.cpp:231`, the `ref_*` tools), so
nothing is lost or leaked now. It is the next call that prints in parts that will be surprised. (The 11-12b audit
removed `flush_pending()`; this is the other half of the same design.)

**Fix:** remember the level of the first piece in `Pending` and let the destructor drop a piece whose level is above
`cfg().level`; or drop a filtered message before appending it, so a `LOG_DBG` never enters the buffer.

## Checked and clean

What "no new crash, heap error, deadlock or wrong result" rests on, by area:

- **`src/http.h` (read in full).** The request line's control bytes; header and body deadlines; the two framings
  refused together; chunk sizes parsed with `from_chars` and bounded before `append`; `Content-Length` bounded by
  `kMaxBody` and by the shared 1 GiB body budget; the 64-connection cap; `no_body` on HEAD; `send_file`'s range
  arithmetic (`y + 1` never past the end, `y >= size` clamped before the add); `client_gone()`'s poll; every exit
  path closes the socket exactly once (`reply_close` closes, the loop's `break` closes, the outer `catch` closes).
  The `on_done` hook runs after the handler's own 500/404 and cannot throw into the connection.
- **`src/log.h` (read in full).** One lock for stderr and `--log-file`; lines split on `\n` with a trailing `\r`
  trimmed; the 64 KB cap for a line that never ends; `vsnprintf`'s return decides truncation; `va_copy` used correctly
  for the two re-uses; exception paths fall back to plain `vfprintf`; the mutex is leaked on purpose so a shutdown
  thread still finds it. Findings 6 and 8 are the two edges.
- **`tools/server_metrics.h` (read in full).** Prometheus' shape (`# HELP` / `# TYPE`, cumulative buckets, `+Inf`,
  `_sum` / `_count`), `num()` handling NaN / ±Inf and whole numbers, `tpot` guarded by `gen > 1`, the two atomics
  clamped at render, no prompt text anywhere, `handler_of` folding unknown paths. `esc` is finding 6.
- **`tools/server_startup.h` (read in full).** Nothing there can stop the start; the environment dump masks secret
  names in any case, replaces the home path and flattens control bytes; the GPU line runs after the NPU.
- **`src/load_progress.h` (read in full).** First and last line always printed, 5 points / 2 s between, a repeated
  percentage never twice; the label is consumed once, so a load that throws does not rename the next one.
- **`src/gguf.h` (read in full).** Bounds written as `n > size_ - pos_` so no sum wraps; alignment checked to be a
  power of two ≤ 1 MiB; every tensor's byte range checked against the mapping; `tensor_bytes` refuses a shape that
  overflows or is not whole blocks; split parts added only if a name is not already present. Finding 2 is the count
  amplification, not a bounds error.
- **`tools/inflate.h` (read in full).** Every read is bounds-checked (`Bits::get`, stored blocks, the Huffman build's
  over-subscription check, the length/distance tables' index checks, `d > out.size()`), output capped by `max_out`,
  ZIP's central directory bounded by the archive size. A damaged stream stops with what was decoded.
- **`tools/server_remote.h` (read in full).** PBKDF2 200k with a per-install salt, constant-time compare, the
  per-visitor and global wrong-password budgets with in-flight attempts counted, `session_gen` invalidating a check
  that started before a settings change, the `Origin` and `https` checks, `head_gate` refusing a body before the
  password, `blocked()` fencing the tool paths a second time, and the Host/proxy check that stops a tunnel which
  rewrites `Host` to `127.0.0.1`.

  linear time, non-finite numbers written as `null`, and `as_int` / `as_clamped` refusing out-of-range numbers before
  the cast.

  every returned handle; the argument cache's generation counter, the launch statistics, `ARC_ZE_WATCH`'s ring and the
  `_Exit` paths are unchanged from the audited version.
- **`tools/server.cpp` (the option parser, the dispatch, the log hook and the model switch in part).**
  `to_int` / `to_double` turn a bad value into a message (not an uncaught `stoi`), and refuse nan / inf; every numeric
  option is clamped at its use; `swap_mu` is shared for a request's whole run and exclusive for a switch, so
  `cur.reset()` cannot race a handler; `save_held()` is called before the reset and takes the engine lock, which no
  handler can hold at that point (the exclusive lock excludes them); the switch's failure path reloads the previous
  variant and leaves "no model" with a 503, not a crash.
- **`tools/server_files.h`, `server_cache.h`, `server_file_tools.h`, `server_projects.h` (in part).** `Store` locks a
  recursive mutex in every public method; `safe_name` strips quotes, CR/LF, path separators, leading dots/spaces and

- **`tools/doc_reader.h`, `tools/pdf_images.h` (the lexer, xref/object streams, page tree, `decode`, the PNG
  predictor, the image headers in part).** The work budget (`512 MB + 3x file`) charges every parse, copy and decode;

## Suggested order

1. **Finding 1** — close the MCP read handles (or hand them to the reader) before the `join()`, as
   `server_terminal.h` already does. One function; it removes the last unbounded wait in the server.
2. **Finding 2** — cap `nkv`, `nt`, `split.count` and an array's element count. Small, and it makes a crafted model
   file fail at the first line instead of after gigabytes of allocation.
