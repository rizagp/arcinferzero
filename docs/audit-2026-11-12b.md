# Static audit, 2026-11-12 (evening): the log, `/metrics` and the rest of the tree

**Status (the same evening):** all 7 findings below are fixed, together with a second, independent review of the same
change (the self audit), whose findings overlapped #2 and #4 and added these:
- **The NPU was hidden:** the start-up GPU line ran the GPU runtime before the NPU's `zeInit(0)`. The GPU line now runs
  after the NPU and speech to text start; `--npu force` on the laptop finds the NPU.
- **Fatal errors logged as `I`, so dropped at `-lv 0`:** ZE_CHECK's "Level Zero error 0x…", the launch errors, a
  missing driver or OpenCL.dll, the expert cache's out-of-memory, and the server's start-up refusals are now `LOG_ERR`.
  The level guess for old calls looks past a tag (`inferzero: `) and for "error 0x", "out of memory" and "device lost".
- **printf format checking lost:** the `LOG_*` macros hand their arguments to an `fprintf` that never runs, so C4477
  checks them.
- **An OCR batch counted as a waiting request for ever:** `/metrics`' in-flight count now starts after the OCR batch's
  per-page calls.
- **No access line for some requests:** the gate's answers (sign-in pages, refusals), OPTIONS, and the refusals before a
  handler (`W HTTP 403, connection closed: …`) are now logged.
- **An inner request's error kept on the outer reply:** cleared by a later success.
- **A failing poll every 2 s:** logged once per path and status, and again after it worked.
- **The memory line could mislead:** it is shown only with a real count, and without "left" for `--slots` / `--gpus`.
- **Secret masking:** names in any case, more words (PASS, KEY, AUTH, CRED, COOKIE), and the user folder in values as
  `%USERPROFILE%`.
- **Rotation edge cases:** a zip is written under a temporary name, and the log is removed only after its zip is in
  place.
- **Smaller:** `/metrics` numbers spell NaN / ±Inf as Prometheus does; a cancelled request counts as
  `finished_reason="abort"`.

Checked on the laptop after the fixes:
- runz's output and logits are identical to release 2026.11.12.12 (4B).
- **The server end to end:**
  - a control byte in the request line → 400 and one W line, nothing forged;
  - an unknown method → `other`;
  - `/metrics`' gauges are empty after an unload;
  - `--log-file` naming stderr's file → refused with an E line;
  - the 4 old logs of 14 zipped, a 100-day-old zip removed.

## 2. The log and the metrics take the request line as it is

**Files:** `src/http.h:509-512` (parsing), `tools/server.cpp:1453-1491` (the access line), `tools/server_metrics.h:115-118`
(the HTTP counter)

```cpp
rq.method = line.substr(0, s1);                       // any bytes up to the first space
std::string target = line.substr(s1 + 1, s2 - s1 - 1);
rq.path = target.substr(0, q);                        // any bytes before '?'
```

`line` is cut at the first **`\r\n`**, not at a bare `\n`, and no byte is validated. Two consequences, both from the new
access line:

```cpp
zlog::log(lvl, "%s %s %d %s %.0f ms %s%s%s%s\n", rq.method.c_str(), rq.path.c_str(), st, sz, ms, ...);
```

- **Log forgery.** A request whose target contains a bare LF (`GET /x\n2026-11-12 14:13:05.123 E GPU: device lost HTTP/1.1`)
  writes a second, fully formed line into `server.log`. ESC (`\x1b`) is passed through too, so the console colours and
  cursor are the client's to drive — and the log is exactly what `zero-server logs`, `zero-server help errors` and the
  launcher show a user, and what a user pastes into a GitHub issue. The same path also reaches the W / E error line,
  which prints `rs.error()` — that one is already flattened (newlines → spaces, `HttpResponse::error_text`), the method
  and the path are not.
- **A metric series per method name.** `zmet::http_done` keys on `{method, handler_of(path), status}`; unknown *paths*
  collapse to `"other"`, unknown *methods* do not, so a client that sends `M1`, `M2`, … `M100000` leaves 100 000 entries
  in `Reg::http` (each `std::string` + `uint64_t`) for the life of the process. A GET that succeeds is only a `D` line,
  but the metrics are updated for **every** request, whatever the verbosity.

Neither is reachable from another site (the Origin / Host checks run first) and both need a client that talks HTTP to the
port, so this is not a break-in; it is text-in-the-log and memory-from-a-label.

**Fix:** in `http.h`, refuse a request line that holds a byte `< 0x20` other than the space, or `0x7f`, with a 400 (one
`memchr`-style scan of `line`, before anything else uses it) — that closes both. Cheaply on top: in `zmet::http_done`,
map an unknown method to `"other"` the way `handler_of` does for paths.

## 3. `/metrics` keeps the gauges of a model that was unloaded

**Files:** `tools/server_metrics.h:69-73` (`loaded`), `tools/server.cpp:2046` (`cur.reset()` in `/v1/server/unload`)

`zmet::loaded()` is called from `load_model()` only. Unloading a model — `POST /v1/server/unload {"which":"model"}`,
or the automatic unload in Settings — does `cur.reset()` and frees the GPU memory, but nothing tells the metrics:

- `model_info{...} 1` still says a model is loaded, with its arch, ctx and GPU count;
- `gpu_memory_bytes` still reports the freed GiB, so a dashboard (or `/v1/server/memory`, which *is* right) disagrees
  with the process' own view — exactly the panel a user watches while freeing memory to load something else;
- `context_max_tokens` and `kv_cache_usage_perc` describe a model that is gone.

The gauges are the `r.model`-labelled block; the counters are per model and are correct to keep.

**Fix:** a `zmet::unloaded()` that clears `model`, `arch`, `ctx`, `gpus`, `gpu_bytes` and `kv_usage` (keeping `m`), called
where `cur.reset()` frees the chat model. `model_info` already skips an empty `model`, so the series disappears cleanly.

## 4. `zlog::flush_pending()` is dead code, and a half line is lost at a crash

**Files:** `src/log.h:202`, `src/crash_log.h:23-30`, `zero/clrt.h:83-89` (`CL_CHECK`), `src/log.h:155` (the 64 KB cap)

The pending-line design (a message printed in parts is held until its `\n`) has an escape hatch, `flush_pending()`, and
nothing calls it:

```
$ grep -rn "flush_pending" src zero tools
src/log.h:202:inline void flush_pending() noexcept {
```

Consequences, all small:

- `_Exit(1)`, which the GPU checks use (`CL_CHECK` / `ZE_CHECK` print their line, then `_Exit` to skip destructors), runs
  no destructor, so a partial line written earlier by that thread is dropped. Every one of those messages ends with
  `\n` today, so nothing is lost *now* — it is a trap for the next call that prints in parts.
- `crash_log` writes with plain `fprintf(stderr, ...)` (deliberately, so the report never waits on the log's lock). A
  partial line another thread is holding is therefore not on the stream, and the crash's first line starts on its own —
  but the held text is never written, and if the crash happens on the thread that holds it, it is simply gone.

**Fix:** either delete the function (and the claim that a line is flushed before a crash), or call it from
`crashlog::filter` **through a `try_lock`** — never a plain lock: a thread that crashed while inside `emit()` still holds
`zlog::mu()`, and a blocking flush there would hang the handler (the process would hang instead of dying, which is
worse than losing a line). If that is not wanted, say in `docs/logging.md` that a partial line is lost at a crash.

## 5. The four usage texts are not in the log

**Files:** `tools/server.cpp:1206`, `zero/runz.cpp:257`, `zero/transcribez.cpp:69`, `tools/zero_recorder.cpp:412`

Every other message in `src/`, `zero/` and `tools/` now goes through the log (375 `zlog::*` calls, 41 `LOG_*`), except
these four `--help` blocks. In `runz`, `transcribez` and `zero_recorder` the log is off, so they print as before and
nothing changes. In `serverz` the log is **on**, so `serverz --help` (and a wrong option's usage line) appears among
prefixed lines, without a time or a level, and never reaches `--log-file`.

**Fix:** `zlog::raw(...)` (no prefix, kept as it is) or `LOG_INF` for each; they are one format string each.

## 6. `--log-file` can be the log the launcher is already writing

**Files:** `tools/server.cpp:1026-1030` (`--log-file`), `scripts/zero-server.ps1:1233` (`-RedirectStandardError $log`)

`zero-server` starts the server with stderr redirected to `%USERPROFILE%\.inferzero\server.log`; `--log-file F` opens
`F` with `"ab"` for a second copy. A user who reads `docs/logging.md` ("the server writes its log to stderr, zero-server
sends it to `…\server.log`") and adds `--log-file %USERPROFILE%\.inferzero\server.log` to the extra options gets two
writers on one file: the redirected handle was created by PowerShell without append semantics, so it keeps its own
position while the append handle always writes at the end — lines overwrite each other.

Two smaller points in the same place: the file is opened once and grows without a bound (no rotation, unlike `logs\`),
and it is never closed (harmless — every line is flushed).

**Fix:** refuse (with a clear message) a `--log-file` that has the same full path as `stderr`'s target, or at least say so
in `docs/logging.md`. The rotation is a doc note: "`--log-file` is not rotated; use `logs\` for that".

## 7. Three small drifts between `docs/logging.md` and the code

1. **`--log-colors on` in a redirected log.** The doc says "colors for W / E / D; auto: in Windows Terminal, never in a
   redirected log". `auto` is right (`zlog::start`: `WT_SESSION` *and* `_isatty`); `on` is explicit and does write ANSI
   into `server.log`. Fine behaviour, but the table row reads as if a redirected log never had colours — worth one
   sentence.
2. **The crash report never reaches `--log-file`.** `docs/logging.md` says "`--log-disable`: no log; a crash report is
   still written", which is true (it goes to stderr, hence to `zero-server`'s `server.log`), but with `--log-file F` the
   report is the one thing that is *not* in `F`. One sentence.
3. **"The ~390 old `fprintf(stderr)` calls"** (CHANGELOG): today it is 375 `zlog::*` calls plus 41 `LOG_*` calls; the
   exact number does not matter, but the claim is now unverifiable as written. Better: "the calls in `src/`, `zero/` and
   `tools/`, except the four usage texts and the crash report (finding #5)".
